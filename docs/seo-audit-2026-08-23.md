# SEO Audit — elitebcn.info

**Date:** 2026-08-23 · **Business type:** Local Service (VTC chauffeur, Barcelona) · **Scope:** 98 indexable URLs

## Method & limits — read this first

The live site could not be reached from the audit environment (network policy denied
`www.elitebcn.info`; the proxy answered 403 to CONNECT). **Nothing here is a
measurement of production.**

Every finding below comes from one of two sources, and each is labelled:

- **Built** — a production build of this repo (`next build`, Next 16.2.6) served locally and
  crawled: all 98 sitemap URLs fetched, HTML parsed for metadata, headings, images, links
  and JSON-LD; Lighthouse (Chromium, mobile emulation) on 5 representative pages.
- **Code** — read directly from the repository.

Consequences of the limit: no Search Console data, no field Core Web Vitals (CrUX), no
SERP positions, no backlink profile, no Google Business Profile signals, and no
confirmation that production serves what this build serves. The largest untested
assumption is #2 below.

## What the crawl found clean

Worth stating plainly, because it narrows where effort should go. Across all 98 URLs
(**Built**):

- 98/98 return 200. No redirect chains, no soft 404s in the sitemap.
- 98/98 have a title, meta description, canonical, and exactly one `<h1>`.
- 0 duplicate titles, 0 duplicate meta descriptions.
- 0 canonical mismatches — every canonical resolves to its own production URL.
- 0 heading-level skips across every page.
- 87/87 images carry an `alt`, explicit `width`/`height`, and lazy loading. No CLS from images.
- 98/98 carry valid, parseable JSON-LD. No deprecated types (no `HowTo`, no `VehicleListing`).
- CLS is **0** on every page measured.
- `robots.txt` allows every major AI crawler explicitly (GPTBot, ClaudeBot, PerplexityBot,
  Google-Extended, Applebot-Extended, CCBot and 12 more), each repeating the disallow list —
  which is the correct way to write it, and a common mistake avoided.

Titles flagged as 61–64 characters by a naive count are 59–60 once `&amp;` is counted as one
character. Not an issue.

## Critical

### 1. `llms.txt` publishes review numbers the codebase knows are false

**Source: Code.** `public/llms.txt:14` and `public/llms-full.txt:135-138` state:

```
Rating: 4.9★ Google (312+ reviews), 4.8★ Trustpilot (189+), 5.0★ TripAdvisor (94+)
```

`lib/company-facts.ts:24-31` records the opposite, and says why:

> this said 4.9 from 312 while /about claimed 595, and the real profile holds 5.0 from 15.
> Trustpilot and TripAdvisor: include only after confirming live profiles exist.

So the site's own source of truth is **5.0★ from 15 Google reviews, with no confirmed
Trustpilot or TripAdvisor profile.** The correction was made in the components and the
structured data; the two files written specifically to be read and quoted by ChatGPT,
Perplexity and Google's AI systems were not updated.

This is worse than an ordinary stale number. `llms.txt` is a document whose entire purpose
is to be trusted verbatim by a machine that will not verify it. It currently invites AI
assistants to tell prospective customers about 595 reviews across three platforms, two of
which do not exist. It also contradicts the `AggregateRating` this same site emits on
`/book` (5.0 / 15) — an on-domain contradiction is exactly the signal that devalues a source.

There is also a legal dimension: under EU Directive 2005/29/EC as amended by the Omnibus
Directive, stating that reviews originate from consumers who used a product, without
ensuring they did, is a listed unfair commercial practice.

**Fix:** replace both blocks with the verified figures from `SOCIAL_PROOF`, and drop the
Trustpilot and TripAdvisor lines until those profiles exist. Better: generate the ratings
line in `llms.txt` from `lib/company-facts.ts` at build time so the two can never drift again.
*(This one is already applied on this branch — see the diff.)*

- **First principle:** a document written to be believed without verification must be the
  most accurate document on the site, not the least.
- **Unblocks:** #4 (GEO). Nothing else in AI-search readiness is worth doing while the
  primary AI-facing document is wrong.
- **How we'd know it failed:** an AI assistant asked "how many reviews does Elite BCN have?"
  still answers 312, or cites Trustpilot, 4+ weeks after the fix.
- **Leading indicator:** the ratings line in `llms.txt` matches `GOOGLE_PROFILE` in
  `data/reviews.ts` on every deploy — assert it in a unit test, not by eye.

### 2. Sitewide `noindex` rests on one build-time environment variable

**Source: Code + Built.** `next.config.ts:74-82` emits `X-Robots-Tag: noindex, nofollow` on
`/:path*` whenever `process.env.VERCEL_ENV !== "production"`. `middleware.ts:8-12` adds a
second guard on the `Host` header. The local build confirms the header fires
(Lighthouse scored SEO 66–69 on every page solely because of it).

On Vercel production this is correct and the intent is right — it stops preview deployments
competing with the canonical domain. The exposure is that `VERCEL_ENV` is read **at build
time**, and its absence means noindex. Any build outside Vercel's production pipeline — a
self-host, a container image, a migration to another platform, a misconfigured project
setting — ships a fully de-indexed site that looks completely normal in a browser.

Rated Critical for blast radius, not for likelihood. It cannot be confirmed either way from
here because production is unreachable.

**Fix:** two parts. (a) Invert the default: gate on an explicit `SITE_ENV=preview` opt-in, so
an unset variable produces an *indexable* site. (b) Add an uptime check that fetches
`https://www.elitebcn.info/` and alerts if the response carries `x-robots-tag`. Verify today
by curling production and reading the response headers.

- **First principle:** a failure mode that is invisible in a browser and fatal to traffic
  must fail loud, not silent.
- **Unblocks:** everything. No other recommendation matters if this fires.
- **How we'd know it failed:** production responds with an `x-robots-tag` header, or Search
  Console reports "Excluded by 'noindex' tag" on canonical URLs.
- **Leading indicator:** the header check in uptime monitoring, running per-deploy.

## High

### 3. The verified 5.0★ rating reaches exactly one page — and hangs off an orphaned entity

**Source: Built.** `aggregateRating` appears on **1 of 98 pages**: `/book`. Not on the
homepage, not on `/pricing`, not on `/about`, not on any of the 58 destination pages.

Worse, on `/book` it sits on a fourth business node. Three `@id`s describe this company:

| `@id` | Type | Emitted by | Carries rating |
|---|---|---|---|
| `#organization` | `Organization` | `app/layout.tsx` — all 98 pages | no |
| `#business` | `TaxiService, LocalBusiness, LimousineBusiness` | `app/layout.tsx` — all 98 pages | no |
| `#org` | `LocalBusiness` | `lib/schema.ts:10` — `/book` only | **yes** |

`#org` is never linked to `#business` or `#organization` by `@id` or `sameAs`. On `/book`,
Google is handed two unlinked `LocalBusiness` entities for the same company, one rated and
one not. Entity ambiguity of this kind commonly suppresses the star rating entirely.

`/book` is also the least useful page to carry it: 436 body words, 9 internal links, a
transactional form. It will not rank for the brand or service queries where review stars
change click-through.

**Fix:** move `aggregateRating` onto the `#business` node in `app/layout.tsx`, sourced from
`SOCIAL_PROOF`, so it ships on all 98 pages. Delete the `#org` node and point
`organisationRef()` at `{ "@id": ".../#business" }`. Google's policy requires the rating
describe the entity it is attached to — a business-level rating on the business node is
compliant; do not copy it onto `Product` nodes.

- **First principle:** a verified trust signal already in the codebase should appear
  wherever it can be shown, on one unambiguous entity.
- **Depends on:** nothing. **Unblocks:** #5 (any schema consolidation).
- **How we'd know it failed:** Rich Results Test still reports no rating, or reports two
  `LocalBusiness` entities, on `/` after deploy.
- **Leading indicator:** Search Console → Enhancements → Review snippets, valid item count
  moving from 1 toward 98.

### 4. Seven fleet pages are 22% unique; the hub links to none of them

**Source: Built.** Uniqueness measured as the share of a page's 8-word shingles, after
removing sitewide boilerplate, that appear on no sibling page.

| Page | Body words | Unique |
|---|---|---|
| `/fleet/eqe-300-electric` | 811 | 16% |
| `/fleet/tesla-model-3` | 808 | 16% |
| `/fleet/executive-minivan` | 800 | 20% |
| `/fleet/standard-sedan` | 798 | 22% |
| `/fleet/business-sedan` | 790 | 24% |
| `/fleet/luxury-minivan` | 802 | 25% |
| `/fleet/group-minibus` | 800 | 30% |

Average 22%, against an 80% threshold for product pages. The word counts look healthy
because the template is long — but 78% of each page is the same prose with the car's name
swapped. That is the classic doorway-page shape.

Compounding it: `/fleet` has 315 body words and **links to zero of its seven children**. All
seven are reachable only from the sitewide footer, giving them the weakest possible internal
signal. `/blog` averages 96% uniqueness over 13 pages, so the capability to write distinct
content clearly exists here — it just was not applied to the fleet.

**Fix, in order:** (a) add a vehicle grid to the `/fleet` body linking all seven with
descriptive anchors; (b) rewrite each page around what is actually different — real luggage
capacity in bags not litres, the specific routes that vehicle suits, what a group of that
size actually experiences, a photo of that car; (c) target 60%+ unique before adding an
eighth vehicle.

- **First principle:** a page that says nothing its siblings do not say has no reason to rank
  separately, whatever its length.
- **Depends on:** nothing. **Blocks:** any expansion of the fleet cluster.
- **How we'd know it failed:** re-run the shingle measurement and uniqueness is still under
  60%; or Search Console shows the seven pages sharing impressions on one query set.
- **Leading indicator:** distinct ranking queries per fleet URL in Search Console — today
  they will overlap almost entirely.

### 5. 22 of 59 destination pages fall below the 60% uniqueness floor

**Source: Built.** At 59 location pages the site is past the 50-page hard-stop threshold for
programmatic location content, which calls for explicit justification per page.

Distribution: 9 pages at 80%+, 28 at 60–79%, **22 below 60%**. The 22 are not scattered —
they are two coherent clusters:

- **20 hotel pages** (`w-barcelona-hotel` 53%, `hotel-arts-barcelona` 55%,
  `mandarin-oriental-barcelona` 57%, …) — the template with a hotel name and address swapped.
- **8 cruise-line pages** (`msc-cruises-barcelona` 53%, `costa-cruises-barcelona` 54%,
  `carnival-cruises-barcelona` 54%, …) — near-identical; every one is the same physical
  journey to the same cruise terminal, differing only in the operator's name.

The cruise cluster is the weaker case. Eight URLs for one route, distinguished by a brand
name the business has no relationship with, is difficult to justify as eight distinct pages.

The 9 pages above 80% (`/transfers/lourdes` at 98%) show what the template supports when
someone writes real detail into it.

**Fix:** consolidate the eight cruise-line pages into one strong `/transfers/cruise-port`
page — which already exists — with 301s from the eight, keeping an operator section on the
target page. For the 20 hotels, add per-hotel specifics only the operator knows: which
entrance the car actually waits at, the drive time in morning versus evening traffic, the
luggage reality of that lobby. Justify each remaining page or redirect it.

- **First principle:** a separate URL has to answer a question the others cannot.
- **Depends on:** nothing. **Unblocks:** adding new destinations safely.
- **How we'd know it failed:** the surviving hotel pages still measure under 60%, or Search
  Console shows them un-indexed as "Crawled – currently not indexed".
- **Leading indicator:** indexed-page count in Search Console holding steady while
  impressions per indexed page rise.

### 6. Six money pages are less than half the length their job requires

**Source: Built.** Body word counts with navigation, header and footer removed:

| Page | Body words | Gate | Gap |
|---|---|---|---|
| `/fleet` | 315 | 400 (category) | −85 |
| `/vip-transportation` | 340 | 800 (service) | −460 |
| `/hourly` | 364 | 800 | −436 |
| `/hotel-transfers` | 368 | 800 | −432 |
| `/day-tours` | 372 | 800 | −428 |
| `/corporate` | 402 | 800 | −398 |
| `/airport-transfers` | 524 | 800 | −276 |

These are the commercial service pages — the ones that should rank for "corporate transfer
Barcelona", "hourly chauffeur Barcelona", "Barcelona day tours by car". `/` has 2,496 body
words and `/faq` 1,349, so depth is not a sitewide problem; it is specific to the pages
carrying the highest-intent queries.

**Fix:** take each to 800+ words of substance, not padding — the corporate page needs
invoicing, account terms, cancellation policy for business travel; the hourly page needs
what four hours actually buys, waiting rules, typical itineraries; day tours needs real
itineraries with timings.

- **First principle:** a page competing on a commercial query has to answer more of that
  query than the pages above it.
- **Depends on:** nothing. **Pairs with:** #7 (breadcrumbs land on the same pages).
- **How we'd know it failed:** word count rises but average position and impressions in
  Search Console do not move within 8–12 weeks.
- **Leading indicator:** number of distinct queries each page draws impressions for.

## Medium

### 7. Breadcrumb markup missing on the 13 highest-value pages

**Source: Built.** `BreadcrumbList` is present on 85 of 98 pages — and absent from exactly
the ones that matter most: `/book`, `/pricing`, `/airport-transfers`, `/corporate`,
`/hourly`, `/about`, `/contact`, `/transfers`, `/tools/transfer-cost-calculator`, `/privacy`,
`/terms`, `/cookies` (and `/`, which correctly needs none).

Breadcrumb rich results are still a live SERP feature, unlike FAQ. The pattern is already
implemented and working on 85 pages; this is a mechanical gap, not a design decision.

- **How we'd know it failed:** Rich Results Test shows no breadcrumb on `/pricing` after deploy.
- **Leading indicator:** Search Console → Breadcrumbs, valid items 85 → 97.

### 8. 74 of 98 pages contain no image at all

**Source: Built.** 87 images exist across the whole site, and they sit almost entirely on
`/`, the fleet pages and the blog. Every one of the 58 destination pages has zero images, as
do `/pricing`, `/airport-transfers`, `/corporate`, `/hourly`, `/day-tours`,
`/hotel-transfers`, `/vip-transportation`, `/about`, `/contact` and `/faq`.

Two costs. Google Images is a meaningful discovery channel for travel and destination
queries, and this site forfeits it on every destination page. And for a service selling on
luxury and trust, an `/about` page with no photograph of the fleet, the team or a vehicle at
the airport is an Experience signal left on the table.

The image handling that does exist is exemplary — every image dimensioned, alt-texted and
lazy-loaded, CLS of 0. The problem is quantity, not quality.

- **How we'd know it failed:** Search Console → Performance → Search type: Image shows no
  impression growth 8 weeks after images ship.
- **Leading indicator:** indexed image count in Search Console.

### 9. Eight languages of translation, none of it indexable

**Source: Code.** `lib/i18n.ts` declares en, es, fr, ar, ru, zh, de, it. `messages/` holds
128 KB of translations. All of it is client-side only: one URL serves every language,
`<html lang="en">` never changes server-side, and `alternates.languages` in
`app/layout.tsx:63-67` declares only `x-default`.

That declaration is *honest* — no alternate URLs exist, so none should be claimed. But the
consequence is that a Barcelona airport-transfer business has **zero indexable Spanish,
French, German or Italian content**, in a market whose inbound demand is overwhelmingly
non-English.

A second, smaller point worth knowing before scoping the work: the translations cover **303
UI strings** across nav, hero, booking flow and footer. No page body is translated. A visitor
who switches to Español gets a Spanish menu above English destination copy. The multilingual
feature is a shell, and it delivers no SEO value and only partial UX value today.

**Fix (largest single opportunity here, and the largest effort):** introduce
`/es/`, `/fr/`, `/de/`, `/it/` routing with server-rendered content and reciprocal hreflang.
Start with Spanish on the top 10 pages only and measure before widening. Do not ship locale
URLs with untranslated bodies — that creates duplicates instead of reach.

- **First principle:** search engines index URLs, not runtime state; content behind a client
  toggle does not exist to a crawler.
- **Depends on:** #6 (translate the improved pages, not the thin ones).
- **How we'd know it failed:** `/es/` URLs indexed but drawing no Spanish-query impressions
  after 12 weeks; or Search Console reports hreflang "no return tag" errors.
- **Leading indicator:** impressions filtered to Spain and to Spanish-language queries.

**Source: Built** (Lighthouse, mobile emulation, local server — production will differ, and a
CDN will likely improve it).

|---|---|---|---|---|---|
| `/` | 84 | 3.4 s | 0 | 350 ms | 83 KB |
| `/pricing` | 92 | 3.3 s | 0 | 70 ms | 62 KB |

CLS of 0 everywhere and FCP of 0.9–1.1 s are both excellent. LCP is the one metric outside

- **Leading indicator:** Search Console → Core Web Vitals, URL group status.

## Low / Info

- **`lib/schema.ts` is bypassed.** Its header reads "Import here; never hand-write JSON-LD in
  page files." One page imports it (`app/book/page.tsx`). The other 97 hand-write their
  JSON-LD. The module is not wrong — it is unused, which is how #3 happened. Route all pages
  through it, or delete it; leaving it as an unfollowed convention guarantees more drift.
- **`FAQPage` on 59 pages — Info only.** Google retired FAQ rich results for all sites on
  7 May 2026, so this markup earns no SERP feature. It is not harmful and **should not be
  removed** on that basis. Do not add it to new pages expecting a Google benefit. Where a page
  is a genuine single-question page with user-submitted answers, `QAPage` is the supported type.
- **`llms.txt` internal inconsistency.** The heading says "Coverage (62 fixed-price routes)";
  two lines later, "all 63 routes" and "63 routes × 5 vehicle classes = 315 fixed prices". The
  file is also stamped "Last updated 2026-07-24", a month stale.
- **Blog posts have no named author.** All 13 carry `author: Organization`. Under the Sept 2025
  QRG, Experience is the weakest leg here — and it is the leg this business should win easily.
  A named driver or founder with a short bio, describing routes they have actually driven,
  converts a generic travel guide into first-hand content.
- **Two meta descriptions at 161–162 characters** (`/book`, `/contact`) — one or two words over.
- **`middleware` file convention is deprecated in Next 16**; the build warns and points to
  `proxy`. Not an SEO issue today, but `middleware.ts` is where the host-based noindex in #2
  lives, so it should not be allowed to rot.
- **`.env.production` is committed.** Secret values are blank, but hostnames and usernames are
  in git history. Not SEO; worth rotating and untracking.
